# Bug 处理流程

Bug 记录用于跟踪一个实际问题及其修复结果。修复工单负责执行代码变更，Bug 记录负责追踪影响、上线和最终验证；两者分别保存，工单结束不会自动关闭 Bug。

## 报告与分诊

在飞书群中 @ 机器人并发送 `/bug 登录后报错，预期进入首页`，或明确描述已经发生的异常。原始消息和附件保留，系统提炼实际表现、预期表现、影响范围与复现线索。模型给出的是建议，不会自动确认根因或分诊结论。

Web 控制台新增「问题」入口，用于管理员登记、分诊、查看历史和处理待办。控制台仍使用原管理员口令；业务用户通过飞书话题和卡片补充、验证，无需取得管理员口令。

每个问题有便于沟通的编号，例如 `BUG-001`。严重程度表示影响大小（S1 至 S4），优先级表示处理顺序（P0 至 P3），负责人可分别调整。

分诊可确认缺陷、认定使用问题、关联同项目的已有需求，或关联已有 Bug 为重复反馈。重复反馈保留自身原话和历史，不自动合并或删除。判断缺信息时标记“等待补充”，保留原环节；补充完成后继续。

转需求需关联同项目的已有需求编号。尚未登记需求时，先通过 `/req` 创建，再在 Bug 话题用 `/bug 新需求 REQ-001 原因` 关联；后续需求梳理在独立话题继续。Web 使用同样的关联规则。

## 修复与关闭

```text
待分诊 → 待复现 → 待修复 → 修复中 → 待上线 → 待验证 → 已关闭
             ↑                                  │       │
             └──────────── 验证失败／重新打开 ────┴───────┘
```

1. 确认缺陷后，记录复现步骤和证据；也可记录由代码、日志或测试证明的定位结果，不强求在生产再次触发。没有复现或定位证据，不能创建修复工单。
2. 请求修复后，编排器预留并关联一个工单，复用现有阶段和 Agent CLI 配置。重复点击或事件重放不会创建第二个修复工单。
3. 修复工单完成后记录修复版本与证据，进入“待上线”。合并代码、测试通过或生成交付报告，都不能替代实际部署。
4. 记录实际部署版本和部署证据后进入“待验证”。验证需基于当前修复轮次及版本，填写实际检查结果；通过才关闭，失败则保留证据并重开原 Bug。
5. 重开后创建新的关联修复工单，旧工单、旧版本和旧验证记录保留供追溯。旧卡片与旧工单完成事件不能处理新轮次。

修复阶段的 skills 继续输出完整交接材料，并明确最小修复范围、相邻功能回归范围及必要的回滚方式。涉及数据、权限和生产配置的变更沿用人工审批，不由 Bug 调查直接执行。

## 展示与恢复

Bug 材料沿用回复展示中的需求收集档位，默认简洁；完整调查依据可展开。展开材料不会启动修复或改变状态。验证失败、调查失败和缺少信息会明确提示，不能伪装成处理成功。

Web 与飞书通过同一状态规则校验版本。每次变更保存操作者、时间、原因和状态前后；旧页面或旧卡片提交时需要刷新，不能覆盖新内容。后台执行请求持久化，服务重启后会继续处理或明确报告中断原因。

运行数据位于 `data/bugs/`、`data/bug-requests/`、`data/bug-cards/` 与 `data/bug-initializations/`，随本地运行数据一起备份。它们含用户反馈、证据和附件，不提交到代码仓库。旧数据无需迁移，新功能使用独立存储。

一期不自动判断重复并合并，不提供 SLA 自动升级、自动生产回滚或跨项目根因分析。
