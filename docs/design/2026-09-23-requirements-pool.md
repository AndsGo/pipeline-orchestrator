# 需求池：工单之前的梳理与排期（设计稿）

**状态**：实现中 · **日期**：2026-09-23 · **范围**：编排器（新增 `src/requirements*.ts`、`handlers/req.ts`、`handlers/pool.ts`，改 `commands.ts` / `daemon.ts` / `threads.ts` / `adhoc.ts` / `feishu/port.ts` / `bitable/*`）；插件只在 clarify 加一句。不动 handoff 契约。

调研与证据见《从一句话到工单》（artifact，2026-09-23）。用户拍板（同日）：负责人点排期；自然语言新需求默认进池、`/new` 直通保留；拆分由 bot 建议、提出人确认时可改；每项目在制工单上限 2。

## 0. 一句话

工单前加一个持久的「需求」对象（`REQ-001`）。bot 在话题里按槽位清单访谈、顺手调研，产出《需求说明》→ **提出人确认** → 进池 → **负责人排期** → 按建议拆分自动建 1–N 张单（每项目在制 ≤ 2，超出排队）→ 全部闭环后在来源话题 @ 提出人。

## 1. 为什么

真实记录（138 次自由对话 / 21 张工单）里已经有一条「先聊需求再建单」的路，但没有载体：09-01 一个需求变两张单无关联；09-04 需求答复落到新会话丢上下文；09-07 bot 让人复制 `/new`；LS-011 提问后 35 天无人答、一直占着工单；LS-012 评估文档被迫建单。

## 2. 状态

```
梳理中 ──提出人确认──▶ 待排期 ──负责人排期──▶ 已排期 ──有名额──▶ 已转工单 ──全部闭环──▶ 已交付
   ▲  └──驳回+意见───┘      └─搁置 / 不做 / 并入 REQ-x（重复）
   └── 提出人在话题里继续补充 = 回到梳理中
```

- `已排期` = 排了但项目在制已满，在队列里。工单闭环事件触发出队。
- `梳理中` 时 bot 判断「不需要改代码」（查数、导出、分析）→ `不做`，备注「无需开发，已在对话中处理」，话题照常可以继续 /run。

## 3. 存储

`data/requirements/REQ-001.json`，编号全局递增（不按项目：需求可能在定项目前就提）。

```ts
interface Requirement {
  id: string; project: string; title: string;
  requester: string;          // open_id
  chatId: string; rootId: string;   // 来源话题（梳理就在这里进行）
  status: ReqStatus;
  raw: string;                // 提出人原话
  brief?: string;             // 最新《需求说明》全文
  splits?: string[]; dupOf?: string; note?: string;
  tickets: string[];
  rounds: number;             // 访谈轮次
  createdAt: string; updatedAt: string; scheduledAt?: string; remindedAt?: string;
}
```

话题记录 `ThreadRec` 加 `req?: string`。不变量：一个话题至多绑一个工单或一个需求（二选一）。

多维表格「需求池」表（`BITABLE_REQ_TABLE_ID`，`scripts/req-setup.ts` 一次性建表）：单向投影，决定只走卡片。

## 4. 入口与分流

| 入口 | 结果 |
|---|---|
| `/req <原话>` | 开需求 |
| 分类器 `req`：描述一件想要的新功能/改进，没说要直接建单 | 开需求 |
| 分类器 `new` / `/new …` / 明确「建单」「直接开工单」 | 照旧直接建单 |
| 会话话题里「整理成需求」「进需求池」「提个需求」 | 以本话题为来源开需求，已有对话算访谈上下文 |
| `/pool` | 列出未关闭的需求（按状态分组，带天数） |

主线里开需求：bot 发一条根消息「📝 REQ-003 需求梳理：…」，访谈在它的话题里进行。

## 5. 访谈（一轮 = 一次只读会话）

复用 /run 的执行体（`execAdhoc`：只读工具 + 只读库 + WebFetch + resume），提示词换成访谈清单：

- 必填槽位：要解决的问题 / 谁用、现在怎么做 / 怎么算做好了（业务验收描述）/ 范围（含、不含）/ 期望时间。
- 自查槽位（bot 自己查，不问人）：口径与术语（注入术语表）、能力定位（`docs/pipeline/system-map/index.md`）、影响面（只读库量化）、疑似重复（注入同项目未关闭需求的标题）。
- 规则沿用 clarify：能查到的不问；每轮 ≤ 3 问，编号，每问 ≥ 2 个选项 + 推荐 + 理由；不问实现；提出人没说的写进「假设」。
- 停止：必填齐就输出《需求说明》（固定模板，以 `# 需求说明` 开头）。第 3 轮起提示词追加「这一轮必须出需求说明，未知项写成假设」。
- 输出 `# 需求说明` → daemon 存 brief、状态 → `待确认`、发确认卡。

《需求说明》模板的节：标题 / 要解决的问题 / 谁用、现在怎么做 / 怎么算做好了 / 范围 / 期望时间 / 口径已确认 / 能力定位 / 调研结论（事实附出处、推测）/ 假设 / 疑似重复 / 建议拆分。daemon 只解析：标题、建议拆分（编号行）、疑似重复（REQ 号）、口径已确认。

## 6. 两道确认

- **提出人确认卡**（gate）：通过 → `待排期`；驳回 + 意见 → `梳理中`，意见作为下一轮自动续聊。提出人或负责人可点。提出人在话题里直接说话（不点卡）→ 旧卡作废，照常续聊，新说明出来再发新卡。
- **排期卡**（choose，只认负责人 `owner`；在话题里发，主线指路并 @ 负责人）：排期 / 搁置 / 不做 / （疑似重复时）并入 REQ-x。项目没配 `owner` 时任何人可点，卡上注明。
- 卡片挂在内存里、重启即失：状态在文件里，**boot 时按状态重发**待确认卡与排期卡（7 天内的）。

## 7. 转工单

- 每条「建议拆分」建一张单（没有就一张）。`requirement` = `来自需求 REQ-003：<拆分项>`；`intakeContext` = 整份《需求说明》+ 把「口径已确认」改写成 `## 澄清问答（需求梳理阶段，提出人已确认）`——clarify 视为已答定论，不重问。
- **在制**：同项目、未闭环、未挂起、且 7 天内有事件的工单。≥ 2 → `已排期` 排队；`done` 事件 → 出队下一条（按 scheduledAt）。
- 工单闭环 → 在来源话题 @ 提出人「REQ-003 的 LS-020 已交付（1/2）」；全部闭环 → `已交付`。
- 待排期超 14 天：每日巡检在来源话题 @ 负责人提醒一次（`remindedAt`）。

## 8. 不做

- 多维表格反向生效（在表里改状态/排序）——等真有人在表里操作再做。
- 池里的需求直接出原型预览（prototype 现在只读 PRD）。
- 访谈评估集（先看真机效果）。
